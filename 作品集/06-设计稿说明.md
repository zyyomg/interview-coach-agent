## 一、这份稿子是什么

面试陪练 Agent 是一个能跑的桌面 Web 产品（本地起服务，浏览器里用）。这份设计稿做的是**把它从「能跑」变成「能被审视」**：三屏主流程、一套组件库、一套设计变量、一条能点通的演示路径。

它不是一个独立的设计练习，而是**同一个产品的一个交付面**。判断它好不好的标准只有一条：**打开设计稿看到的东西，和打开产品看到的东西，是不是同一套东西。**

所以这份稿子的数值不是「看着像」估出来的，是从产品真实的 CSS 里取的（见第五节）。

## 三、一个前置决策：桌面 1440，不是手机 375

产品第一版做过 375 × 812 的手机原型（`04-可点击原型.html`），那是**早期的概念探索**：验证「上传简历 → 语音对练 → 复盘」这条路径能不能说通。

但产品实际落地时是桌面 Web——左侧 304px 固定侧栏放岗位、话题数、难度、简历，右侧是对话主区。原因很直接：

- 一场对练要 10 分钟，用户是在电脑前坐着练的（开着简历、记笔记、查资料）
- 侧栏那 5 个设置项在 375 宽的屏上放不下，只能折叠成抽屉，每改一次设置要多点两下
- 复盘页是「逐题评分 + 参考答法 + 成本明细」的长表格，手机上看要横向滚动

**所以最终设计稿按 1440 × 900 出，和上线产品一致。** 代价是这份稿子没有移动端版本；收益是面试官把设计稿和产品并排开着看，对得上。

如果被问「为什么不做响应式」：产品定位是单人本地练习工具，不做多端；真要做移动端，需要重排信息架构（设置项进抽屉、复盘改成分页），不是把 1440 压窄。

## 四、组件怎么切的

切组件的依据不是「长得像就合成一个」，而是**「会不会一起变」**。

| 组件 | 变体 | 切分依据 |
|---|---|---|
| **Button** | 4 | 两个维度：`Type`（primary / ghost）× `State`（default / hover / disabled） |
| **Seg** | 2 | 单选控件的两个状态：`State`=off / on |
| **Message** | 2 | `Who`=agent / me |
| **Composer** | 1 | 输入条整体（麦克风 + 输入框 + 发送），内部元素不单独成组件 |

### Button 为什么是两个维度，不是四个平铺变体

平铺成 `primary / hover / disabled / ghost` 四个同级变体，做的时候更快，但会丢信息：**primary 和 ghost 是两种按钮，default / hover / disabled 是同一种按钮的三个状态。** 混在一个维度里，「状态」这个概念就消失了，改 hover 色值时要在一堆同级项里找，接手的人也不知道哪两个该长得一样。

拆成两个维度后，规则变成可验证的：同一个 `Type` 下的三个 `State`，**尺寸和内边距必须完全一致，只允许颜色不同**——不一致的话切换状态时按钮会跳。

### Message 只有 2 个变体，这是取舍不是漏做

完整形态有 6 种：提问 / 追问 / 澄清 / 换题 / 收尾（都是 `agent` 侧）+ 我方（`me`）。

只做了 2 个基础变体的理由：气泡的 6 种静态形态在 02 屏里**都有画**（用彩色小胶囊区分：蓝灰 / 琥珀 / 灰 / 紫 / 绿），视觉上不缺；而组件化的价值在「改一处、多处跟着变」，这 6 种形态的差异只有胶囊颜色和文案，复用价值低于维护成本。

**这里诚实地标一句**：如果要做成完整 6 变体，气泡需要改成「透明外壳 + 内嵌气泡框」的两层结构——现在的实现里气泡本身就是变体框，直接往里加胶囊会把框撑变形。这是下一版要重构的地方。

## 五、设计变量与代码同源

设计稿的颜色和字号不是另起一套，是从 `web/style.css` 的 `:root` 里取的。

| 设计稿样式名 | CSS 变量 | 值 |
|---|---|---|
| `accent` | `--accent` | `#2B55D6` |
| `accent-soft` | `--accent-soft` | `#EEF2FF` |
| `ink` | `--ink` | `#12141A` |
| `ink2` | `--ink2` | `#5A6473` |
| `ink3` | `--ink3` | `#98A1B0` |
| `line` | `--line` | `#E6E8EC` |
| `line-2` | `--line-2` | `#EEF0F3` |
| `bg` | `--bg` | `#F4F5F7` |
| `panel` | `--panel` | `#FFFFFF` |
| `amber` | `--amber` | `#A16207` |
| `violet` | `--violet` | `#6D28D9` |
| `green` | `--green` | `#067A5B` |

代码的 `:root` 里共定义 18 个颜色变量（含琥珀/紫/绿/灰/红五组「字色 + 底色」成对变量）。上表是三屏实际用到的主色，设计稿最终建了 12 个颜色样式；标签底色（如 `amber-bg` `#FEF7E0`）在组件里以直接填充呈现，未单独建样式。**12 个样式的完整清单以 Figma 右侧 `Local styles` 面板为准。**

字号这一项的收敛更明显：代码里实际出现了 18 种 `font-size`（9px 到 24px），设计稿收敛成 8 个文字样式。这是设计稿相对代码唯一「变少」的地方——代码是长出来的，稿子得能讲清楚层级。

**为什么强调这件事**：设计稿最容易出的问题是「稿子一套色、代码一套色」，交付时开发要重新对一遍。同源之后，改 `--accent` 一个变量，产品和稿子一起变——这也让「设计稿是产品的一部分」这句话站得住。

## 六、原型怎么连的

三条线，组成一个回路：

```
01 首页 ──「开始对练」──▶ 02 对练中 ──「结束」──▶ 03 复盘 ──「再练一场」──▶ 01 首页
```

| 跳转 | 动画 | 为什么 |
|---|---|---|
| 01 → 02 | Smart animate，300ms | 开始对练是「进入一个状态」，需要过渡感 |
| 02 → 03 | Smart animate，300ms | 结束后停在原地看报告，滑入比硬切自然 |
| 03 → 01 | **Instant** | 回到起点是「重开一局」，不是「过渡到另一页」。这里做淡入淡出，观感像卡了一下 |

`01 首页` 画板设了 `Flow starting point`，所以按 ▶ 一定从首页开始，不会从中间某屏起。

## 七、怎么验（给面试官的 90 秒路径）

1. 打开设计文件链接 → 停在 `说明` 页（封面，写了产品是什么、文件里有什么、怎么看）
2. 左侧 `页面` 页 → 三屏并排，1440 × 900
3. 右上角 ▶ → 点「开始对练」→ 点「结束」→ 点「再练一场」，回到首页
4. 左侧 `组件` 页 → 四组组件，点开右侧面板能看到 `Type` / `State` / `Who` 这些属性

**如果只给 HR 30 秒**：直接给 `/proto/` 链接，打开就是首页大图，点两下就能看到主流程，看不到图层和工具栏。

## 八、已知不足

写在这里，比被问出来强。

- **设计稿是产品做完之后反推的**，不是先设计后开发。真实顺序是：先写 HTML/CSS 让它能跑，再把已上线的界面重搭进 Figma。所以在「设计驱动开发」这一点上，这份稿子不能证明；它能证明的是「能把一个已存在的产品抽象成可复用的设计系统」。
- **Message 只有 2 个变体**，完整 6 种形态在 02 屏以静态图层呈现，未全部组件化（原因见第四节）。
- **没有移动端适配稿**（原因见第三节）。
- **三屏里部分元素仍是直接绘制的图层**，未全部替换为组件实例——改主组件时不能保证三屏全部联动。这一项是交付时明确留下的待完善项。
- **没有交互动效稿**：hover、focus、录音中的状态点在 CSS 里有实现，设计稿里只定义了颜色，没有做多帧演示。
